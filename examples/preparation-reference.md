# 开发准备填写示例

这是虚构的“收藏参考链接”需求示例，用于展示文档应写到什么程度。它不是本仓库的业务目标，没有实现代码，也没有安装、运行或兼容性验证。下面的规则只适用于示例，不自动适用于其他插件。

## 用户需求与验收

示例需求：用户在 DSH 页面保存参考链接，Agent 能搜索已保存记录，重启后继续使用。本次只保存用户提交的标题和链接，不抓取网页内容。

| 编号 | 用户动作与输入 | 期望结果 | 当前状态 |
| --- | --- | --- | --- |
| A1 | 页面提交标题与 HTTPS 链接 | 新记录出现，工具能查到相同标题和链接 | 计划 |
| A2 | 提交无法解析的链接 | 提示修正输入，不新增记录 | 计划 |
| A3 | 成功保存后重启宿主 | 页面与工具仍能找到记录 | 计划 |
| A4 | 禁用后重新启用插件 | 入口和工具恢复，各自只注册一次 | 计划 |

示例假设：首次使用只处理单个本地用户；默认保留卸载后的收藏数据。如果真实用户提出其他要求，应先修订这些约定。

## 能力、结构与依据

需要 Client 页面、Host 收藏服务、搜索工具和本地持久化。页面与工具复用收藏服务的校验和读写；本期没有独立 HTTP 服务或抓取进程的需求。

| 职责 | 拟实现方式 | 与验收的关系 |
| --- | --- | --- |
| 收藏操作 | 一个服务负责输入校验、保存和查询 | A1、A2 |
| 持久化 | 先依据数据量与故障恢复要求选择方案；写入成功后才通知 UI | A3 |
| 页面与工具 | 分别作为收藏服务的入口，工具返回便于模型理解的记录摘要 | A1、A2 |
| 插件生命周期 | 注册和释放入口、工具与订阅，数据按约定保留 | A4 |

文件结构暂不画完整目录树。核对目标版本入口和构建方式后，为上述实际职责建立最少文件；若职责增长再拆模块。这样需求能指导结构，也不会先制造空目录。

## 环境记录与首个验证任务

| 项目 | 示例中的事实状态 | 下一步 |
| --- | --- | --- |
| 运行 DSH 版本 | 尚未选择 | 检查已有安装，选定精确版本并登记 |
| 官方参考 | 本 base 已有固定提交索引 | 核对目标版本的工具、Slots 与包声明 |
| 宿主查询/安装工具 | 未检查 | 查看本次会话可用工具；缺少时核对本地 CLI |
| 目标系统 | 用户尚未给定 | 若影响存储或分发，明确需求；不从开发机推断 |
| 实际运行命令 | 尚未建立 | 选择运行基线后编写并执行，再登记为可用 |

第一项实施任务是验证最小安装包：可以加载一个入口或工具，随后禁用并确认移除。只有这条路径跑通，再扩展收藏行为；不能预写“已支持某版 DSH”或猜测一条启动命令。

## AGENTS 应如何补充

此例中适合成为长期规则的是：收藏数据由同一服务拥有；页面和工具使用相同校验；卸载保留数据。补充时标明这些是示例项目的产品选择，并链接项目说明。

“正在排查工具未注册”“明天补一张截图”“准备尝试某存储库”等属于本次任务状态，留在任务记录，不进入根 AGENTS。

## 完成时如何记录

按 A1—A4 保存真实环境、代码版本、执行动作与观察结果。此示例没有执行，所以状态继续是计划。实际项目中即使 A1 的单元测试通过，也不能据此将 A3 的重启或 A4 的生命周期标为通过。

文档质量反例：只写“支持收藏、结构合理、测试通过”。合格记录应能回答保存了什么、由谁保存、什么时候算成功、工具读到什么，以及哪条证据支持哪项结论。
