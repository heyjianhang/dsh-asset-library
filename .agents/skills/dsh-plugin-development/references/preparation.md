# 开发前准备

本流程用于补足当前任务缺少的信息。已有依据直接复用，不要求每次重建文档。

## 先读现状

读取根规则、适用目录规则、现有项目说明及相关代码，检查未提交改动。识别用户此刻要求的是调研、实施还是评审，保留已有成果和规则。

新项目至少弄清目标用户、要完成的动作、输入与输出、可观察验收。确认是长期可安装插件、临时实验还是配置连接器；这些交付方式的结构和验证入口不同。

## 形成足够的设计依据

按实际需要考虑：

- **能力归属**：哪些事情宿主已有，插件要补什么；需要 Host、Client、工具、外部进程或存储中的哪些部分。
- **运行条件**：目标宿主准确版本、开发方式、操作系统、必需/可选依赖；当前 Agent 可用的查询、浏览器和安装工具。
- **数据边界**：谁拥有数据，多个入口如何共享校验，重启和卸载后应发生什么。
- **文件结构**：现有文件如何修改，需要新增哪些职责；只有职责已经明确才创建文件，复杂到需要拆分时再拆分。
- **验证路径**：怎样从构建包验证安装与业务结果；缺少某种环境时明确后续验证范围。

接口依据优先看目标版本的实际声明、可用运行时查询与对应提交文档。运行时查询得到的“当前未挂载”与声明“不存在”不同。示例和社区文章有冲突时核对版本及场景，不混合不同代接口。

## 选择适量文档

撰写前读取 [文档规范](../../../../docs/documentation-standard.md)，按照内容职责、契约字段、状态和证据要求填写。它明确“写什么”和“什么时候更新”，这里负责选择本次需要的准备工作。

新插件可先用一份 [项目说明](../../../../templates/project-brief.md) 合并需求、架构、基线和验收；复杂后再拆文档。这里给出的是内容参考，文件名与目录由当前仓库决定。

非简单变更可使用 [变更计划](../../../../templates/change-plan.md)。已有任务记录时直接更新，不为相同目的再建一份。小修复只需明确相关规则、修改点和验证结果。

更新根 AGENTS 中的文档入口，让新会话能够找到真实资料。局部目录需要不同规则时再建立局部 AGENTS，并说明适用范围。

首次编写可以对照 [填写示例](../../../../examples/preparation-reference.md)：需求要对应验收，结构选择要对应职责，未知环境要有核对动作；不要照搬示例的业务模型或目录。面向最终用户的安装与使用说明可参考 [README 模板](../../../../templates/plugin-readme.md)。

## 更新 AGENTS 的判断

会持续影响后续开发的约束、接口边界、工具链、命令或文档入口进入 AGENTS。单次需求、待办、猜测、运行日志和尚未落实的命令留在项目或任务记录中。

保留已有用户决策。将新增规则标明为用户要求、目标版本接口要求或项目选择，并说明范围；避免把某次 workaround 写成所有插件的永久限制。可参考 [规则补充模板](../../../../templates/project-rules.md)，不要用模板整份覆盖现有 AGENTS。

## 进入开发

目标、验收、相关接口、改动范围和验证路径明确后即可继续，不以“所有文档填满”为开始条件。可逆实现选择由 Agent 根据已有信息决定，说明关键假设；无法推断且影响方向的问题集中询问，同时继续不依赖回答的工作。

资料来源已锁定但真实宿主未跑通时，先实现最小加载验证，避免把未经验证的结构扩散成多个业务模块。用户只要求规划时停在规划交付。
