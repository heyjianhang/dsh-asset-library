# 独立插件文档规范

本文规定开发前需要形成什么记录、如何维护，以及什么证据能支持交付结论。文件名和目录可以由项目选择，小项目可合并文档；内容职责不随文件合并而省略。

这是本 base 对官方文档原则的适配，适用于使用本 base 的独立插件项目，并非 DSH 官方发布的规范副本。[来源映射](source-map.md) 区分官方依据、适配和本地约定；完整填写方式见 [准备示例](../examples/preparation-reference.md)。

## 1. 哪些内容放在哪里

| 内容职责 | 最少需要交代 | 触发更新的变化 |
| --- | --- | --- |
| 根 AGENTS | 每次会话必须知道的规则、适用范围、文档入口和真实命令 | 长期约束、工具链、入口改变 |
| 项目需求 | 使用者、触发场景、输入输出、可观察验收及关键边界 | 用户目标或完成条件改变 |
| 设计说明 | 所需宿主能力、模块与数据所有者、调用方向、生命周期及结构理由 | 职责、接口、存储或依赖改变 |
| 当前任务记录 | 此次目标、影响文件、实施顺序、状态、证据和下一步 | 非简单任务推进或中断接续 |
| 使用说明 / README | 用户得到什么、前提、安装使用、配置、失败处理、限制 | 安装、公开行为或配置改变 |
| 验证记录 | 对应的验收、环境、代码版本、真实动作和观察结果 | 执行验证或相关实现改变 |

同一事实只在其所属位置维护，其他位置通过链接引用。详细参数、类型和工具清单已有源码或生成器时链接它们，不再人工复制一份完整目录。

## 2. 开发前留下足够的依据

新项目或非简单功能开发，在现有文档或新建记录中写清下面五项。它们是内容要求，不要求分别建立五个文件。

1. **目标与验收**：写用户动作、成功结果和相关失败结果。避免仅写“支持搜索”“界面友好”。复杂任务可给验收编号，方便连接设计与证据；小任务无需编号。
2. **环境与接口依据**：写准确宿主版本或待核对项、所需能力、当前可用工具、官方文档提交或实际类型位置。研究基线与运行基线分开。
3. **设计及文件影响**：写职责、调用方向、数据归属、拟改动的文件，以及为什么需要新增模块。结构未确定时先描述职责；不预建空目录。
4. **实施与验证路径**：写第一条可验证流程，关联验收动作；新运行基线优先安排构建产物的真实安装、调用或显示及卸载。
5. **假设与未决项**：说明会影响实现的假设及其依据；关键未知点明确下一步如何核对，不以模板中的默认答案代替事实。

上述信息足够支持下一步时进入开发；不等待所有可选设计完成。简单修复复用已有需求与设计，在任务记录或交付说明中补修改点和验证即可。

## 3. 契约写到可执行的程度

只记录当前插件实际提供的能力。一个操作有多个调用入口时，说明它们共用哪项业务逻辑。

| 涉及能力 | 说明中必须覆盖 |
| --- | --- |
| 公共服务 / 工具 | 使用场景、调用前提、关键参数约束、结果区别、副作用、可恢复错误；重复调用、取消、超时等仅在涉及时说明 |
| UI | 用户入口、交互结果、加载/空/失败状态、键盘与可访问性需要；采用的 Slot、组件与主题依据 |
| 数据 | 数据所有者、保存位置、成功写入的含义、重启与卸载行为；涉及升级时说明兼容与迁移 |
| 外部依赖 | 必需还是可选、缺失时行为、配置位置、失败如何呈现与恢复 |
| 后台资源 | 谁启动、如何停止、重载后是否恢复、如何确认没有重复注册或残留资源 |

只写“失败抛错”通常不够：应交代什么条件失败、是否已经产生副作用、调用者应修正输入还是重试。源码类型已经表达清楚的字段不必逐项重述，记录调用者看类型仍无法判断的行为。

## 4. 写使用说明与操作步骤

先查包事实再选择说明形式：配置 bundle 说明加入 profile 后获得什么；可加载插件说明宿主挂载方式；普通库说明导入与调用。不要因目录名带 plugin 就写安装命令。

每条操作路径给出：前提 → 实际命令或用户动作 → 可观察成功结果 → 常见失败及恢复。涉及命令时注明工作目录、必要环境和参数含义；敏感值以变量表达。

已执行且可复现的命令才能写成“已验证可用”。待执行的步骤留在计划中并标明状态；外部文档中的命令标注来源和待适配环境。操作未验证时说明缺少什么，不能补写预期输出作为实测结果。

使用说明按读者完成动作的顺序组织；参考说明按查找对象组织。内容较长才增加目录或拆页，不强制所有文档复制相同标题、YAML 元数据或双语文件。

## 5. 状态、证据与更新规则

项目设计可以包含计划，使用说明描述实际可用能力。混合记录时显式区分：

| 状态 | 含义 |
| --- | --- |
| 计划 | 已决定或拟采用，代码尚未完成 |
| 已实现，未验证 | 代码存在，但对应行为尚无验证证据 |
| 已验证 | 指定代码版本、环境和路径中的观察结果符合要求 |
| 未覆盖 | 缺少环境或本次未执行，明确影响哪项结论 |

验证记录至少保留：日期、环境、代码版本（有未提交修改时注明）、命令或用户动作、实际结果、失败或未覆盖范围。可以链接精简日志、测试输出或截图；截图不替代存储和生命周期验证。

代码与文档在同一次变更中保持一致：接口变化更新接口所有者的说明；文件移动修复入口和引用；命令变化更新使用说明；长期规则变化更新 AGENTS。实现结束后清理已失效的待办，保留重要设计原因与真实证据。

## 6. AGENTS 怎么更新

每次开发前检查适用规则。只有长期规则、真实命令或资料入口改变时修改 AGENTS；本次排查过程、临时待办和假设留在任务记录。

新增规则交代来源为用户要求、上游接口要求或项目选择，并说明适用范围。保留用户已确定的规则，不因当前实现困难而放宽。局部规则放在受影响目录的 AGENTS，根文件保留入口。

操作依据以当前项目的已验证事实为准。上游规则的适用范围不能擅自扩大，例如宿主仓库自己的包命名、翻译配对和网站构建不自动成为独立插件要求。

## 7. 提交前的文档检查

逐项判断本次受影响的内容：

- 新读者能找到项目目的、当前规则、下一步和成功标准。
- 需求中的验收在设计或验证记录中能找到对应实现和证据，未完成项没有消失。
- 结构记录与实际文件一致，计划结构已标注，所有新增目录有具体职责。
- 官方约束有版本与来源，项目选择没有伪装成官方要求。
- 操作、默认值、平台差异和完成状态有相应证据或明确的未验证标记。
- 相关链接有效，生成内容未被手工修改，不重复维护类型和完整 API 清单。

`node scripts/check-base.mjs` 只覆盖链接和入口等机械检查。上述语义判断由维护者审阅；完整开发行为按 [Agent 场景协议](agent-scenarios.md) 另行验证。
